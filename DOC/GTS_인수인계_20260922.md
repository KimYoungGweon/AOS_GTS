## 2. 프로토콜 세 가지 — 헷갈리기 쉬움

### 2-1. 콘솔 ↔ 서버 (UDP 5502)

```
STX TYPE ID CMD SIZE(2LE) DATA[SIZE] CRC16(2LE)
                          └ 앞 4 byte = src_type, src_id, seq(2LE)
CRC16-MODBUS, TYPE~DATA (STX 제외)
```
**seq 가 DATA 안에 있다.** 헤더 6 byte.

### 2-2. 서버 ↔ 브리지 (UDP 5500 AOS / 5501 GFC)

```
STX DTYPE DID CMD SEQ(2LE) SIZE(2LE) DATA[SIZE] CRC16(2LE)
CRC16-MODBUS, DTYPE~DATA (STX 제외)
```
**seq 가 헤더에 있다.** 헤더 8 byte. GFC·AOS 가 완전히 같은 프레임이고 DTYPE 만 다르다
(1=AOS, 2=GFC). 명령 대역은 GFC `0x30~0x3A`, AOS `0x40~0x4F`.

### 2-3. 브리지 ↔ STM32 (UART2)

| | GFC | AOS |
|---|---|---|
| Baud | 115200 | **38400** |
| SIZE 필드 | 1 byte | **2 byte** |
| 체크섬 | `255 - Σ(CMD~DATA)` | 동일 |
| 주요 CMD | `0x70/0x71/0x72` | `0x2A/0x52/0x02` |

**①②③ 이 전부 다르다. 변환은 서버와 브리지가 나눠 맡는다.**

### 명령 변환표

| 콘솔 | → 서버 → | 브리지 | → | STM32 |
|---|---|---|---|---|
| `0x20 GFC_SET_MODE` | | MANUAL 이면 `0x34 SRC_SET(enable=0)` | | `0x70` |
| `0x21 GFC_SET_PUMP` | | `0x30 PUMP_SET(on,on,on)` | | `0x70` |
| `0x22 GFC_SET_TIMES` | | 저장, 동작 중이면 `0x34` 재전송 | | — |
| `0x23 GFC_AUTO_RUN` | | `0x34 SRC_SET(enable,init,cycle,600)` | | `0x70` |
| `0x40 AOS_SET_PARAM` | | `0x40 PARAM_SET` (8 byte 그대로) | | `0x2A` 또는 `0x52` |
| `0x41 AOS_SET_LF_MODE` | | `0x41 LF_MODE` | | `0x52` |
| `0x42 AOS_SET_LF_SHAPE` | | `0x42 LF_SHAPE` | | — (eSquare 고정) |
| `0x43 AOS_GET_PARAMS` | | `0x43 PARAMS_QUERY` | | `0x02` |

역방향: GFC `0x32 SENSOR_DATA` → 콘솔 `0xA3 GFC_AUTO_STATE` /
AOS `0x44 AOS_PARAMS` → 콘솔 `0xC3 AOS_PARAMS` (26 byte 무손실 전달)

## 4. 네트워크 ⚠️

```
ESP32 브리지 ── OFFICE_SSID (Google Nest WiFi, 192.168.86.0/24)
                      │ NAT
                      ▼
               192.168.0.30 (Nest 의 WAN)  ──  서버 192.168.0.6
```

- **브리지들이 서버와 다른 망에 있다.** Nest WiFi 가 NAT 로 중계한다
- 서버에는 두 브리지가 **같은 IP(192.168.0.30)** 로 보인다 — IP 충돌이 아니라 NAT다
- 서버가 "패킷이 온 주소 그대로" 되돌려 보내므로 동작한다 (아래 E2)
- **약점**: 상향이 멎으면 NAT 매핑이 만료되어 하향도 끊긴다. 브리지가 1초마다
  상향을 올려 유지하는 중이다. 서버가 먼저 말을 걸 수는 없다
- 콘솔은 외부 IP `218.147.152.41:5502` 로 보낸다 (헤어핀 NAT)

**정리하려면** Nest 를 브리지 모드로 바꾸거나, 브리지를 192.168.0.x 망 AP 에 붙인다.
고정 IP 를 쓸 거면 `*_config.h` 의 `*_STATIC_IP` 가 **실제 붙는 망의 서브넷**이어야 한다.

## 5. 설계 결정 (E 시리즈)

`DOC/GFC_제어경로_테스트.md` 5절에 근거가 자세히 있다.

| # | 결정 |
|---|---|
| E1 | 서버→브리지 하향은 **직접 송신** (ACK 동봉 아님) |
| E2 | 브리지 주소는 **수신 패킷의 source 주소** 그대로 — NAT 뒤에서도 동작 |
| E3/E4 | `cycle_count` 는 서버가 `SRC_ON` 상승 에지로 센다. 초기 주입 제외용 `flags` bit4 = `SRC_INIT` |
| E5 | 수동 `PUMP_SET` 이 주입 시퀀스를 정지시킨다 |
| E6 | GFC `period_sec` 600 고정 (콘솔에 주기 입력 UI 없음) |
| E7 | 주기 분사는 init 종료 후 1주기 뒤부터 |
| E8 | `GFC_AUTO_STATE.pump` 는 **장비가 보고한 실제 Pump2** (`src_on` 아님) |
| E9 | 콘솔에 **로컬 조작 우선 구간** `GTS_LOCAL_HOLD_MS` 1200ms — GFC·AOS 공통 |
| E10 | 서버발 `PUMP_SET` 은 값이 같아도 UART 재전송 |
| E11 | `gfc_uart_pump_set()` 이 캐시를 낙관적 선반영 |
| E12 | UART 폴링을 100ms 틱 + expedite 로 |
| E13 | 서버는 `run`/`pump` 가 바뀌면 즉시 push |

### AOS 에서 STM32 소스를 읽고 알아낸 것 ★

문서만 봤을 때의 추측과 달랐던 것들. `DOC/GTS_AOS_Bridge.md` 1절에 자세히 있다.

- 개별 파라미터 명령(`0x01/0x21/0x26/0x27/0x52`)이 **실제로 구현돼 있다**
  (문서는 "Legacy, 미사용" 으로 적어 두었으나 H753 펌웨어에 살아 있음)
- `SET_Control()` 이 메인 루프에서 `SET` vs `OSET` 를 비교해 적용한다 → **값만 쓰면 된다**
- `CMD_SET_CONTROL`(0x2A) 16 byte 로 HV·Frq·Duty·CV 를 한 번에
- `CMD_LF_MOD_SET`(0x52) 10 byte 가 LF type·OnOff·amp·frq 를 전부 덮는다
- ⚠️ **`0x02` 응답은 CV 가 두 번째** (HV→CV→Frq→Duty). 송신 `0x2A`(HV→Frq→Duty→CV)와 다르다
- ⚠️ offset 17/23/27 의 float 은 **비정렬** — `memcpy` 로만
- ⚠️ **LF 파형 번호가 콘솔과 STM32 가 전혀 다르다.** 지금은 `eSquare(6)` 고정
- DUTY 실제 범위는 **20~80 %** (사양서 초안의 10~50 은 틀림). 콘솔·브리지 모두 수정 완료
- STM32 USART2 = **PA2(TX) / PA3(RX)**, 38400 8N1

## 6. 웹서버 / API / DB — **설계 확정, 구현 대기**

### 6-1. 지금 상태

**DB 설계가 끝났다.** 6-3 의 W1~W7 과 후속 결정 D1~D16 이 전부 확정됐다.

| 문서 | 내용 |
|---|---|
| `DOC/GTS_DB_Design/GTS_DB_Design_Proposal_v1.md` | 설계 근거 · 구조 · 용량 산정 (v1.3) |
| `DOC/GTS_DB_Design/schema.sql` | **실행 가능한 DDL** (PostgreSQL 14+, 파서 검증 완료) |

`udp_server.py` 는 **아직 손대지 않았다.** 여전히 상태를 메모리에만 들고 있다.

### 6-2. 확정 구조 — 데이터를 **수명**으로 세 계층에 가른다

| 계층 | 대상 | 수명 | 방법 |
|---|---|---|---|
| **A. 영구** | run / grid / heatmap / 비교결과 | 무기한 | 일반 테이블 |
| **B. 휘발** | GFC 1초 텔레메트리 | run 종료 시 | `UNLOGGED` + 파티션 `DROP` |
| **C. 비저장** | AOS Current 1초 | 수 분 | **DB 안 씀** — 서버 메모리 `deque` |

이 분리가 **TimescaleDB 를 불필요하게 만들었다.** 보존 정책이 `DROP TABLE` 한 줄로 끝나고,
수천만 행을 `DELETE` 할 일이 없으니 bloat·autovacuum 문제도 생기지 않는다.

**Twin → Single 변경의 반영**

- Air 와 Target 은 **각각 별도 run** (`run.kind = 'air_ref' | 'gas'`)
- Air 는 **여러 개 공존**하고, 대시보드에서 **사용자가 매번 직접 고른다** (자동 선택 없음)
- `Idf = Target_P − Air_P` 는 **저장하지 않는다.** 조회 시 계산, 요약만 `pair_stat` 에 캐시
- **"두 run 을 짝지어 뺀다" 가 단일 연산** → Idf 계산과 **장치 간 편차 비교가 같은 코드**
- refinement(FineTrace) 는 **동작 자체가 삭제**되므로 대응 테이블 없음

**부수 효과 — UDP 단편화가 사라진다 ★**

Positive 1채널 + 16×11 격자 = **352 byte/heatmap.**
RS232 `0x86` 의 8,576 byte 와 달리 **1 datagram 에 heatmap 1장**이 들어간다.
재조립·부분손실 처리가 통째로 불필요하다. 8시간 Full 모드에서 이 이득이 가장 크다.

### 6-3. 결정 결과 (W 시리즈 + D 시리즈)

| # | 항목 | 결정 |
|---|---|---|
| W1 | UDP 서버와 API 서버 분리 여부 | **한 프로세스** (asyncio 한 루프에 FastAPI). DB 는 로컬 |
| W2 | DB 엔진 | **PostgreSQL 단일.** TimescaleDB·SQLite 아님 |
| W3 | 스키마 분리 | **수명 기준 3계층** (6-2) |
| W4 | 쓰기 부하 | heatmap 단건 즉시 / GFC 1초는 **5초마다 `COPY`** |
| W5 | 대시보드 실시간 | **WebSocket** (AOS Current 는 DB 경유 없이 deque → 푸시) |
| W6 | 웹 제어 | **한다.** `device_lock` 소유권 임대 + `control_action` 감사로그 |
| W7 | 인증 | 사내 전용. **DB 포트 비공개**, API 토큰 `read/control/admin` 3단계 |
| D1 | GFC 원본 1초 | 버리되 **10초 평균 다운샘플 보존** (run 당 ≈230 KB) |
| D11 | AOS Current | **DB 미사용.** 메뉴얼 모드 전용 실시간. 측정 중엔 올라오지도 않음 |
| D13b | Air 선택 | **사용자 선택 필수.** 자동 추천·기본값 없음 |
| D14a | 락 정책 | **콘솔 무조건 선점** — 장비 앞의 사람이 이긴다 (E9 와 같은 원칙) |
| D14b | run 중단 | **중단 후 이어서 재개 가능.** `status='paused'` + 남은 `cond_idx` 만 재측정 |
| D16 | 기존 `.dat` 샘플 | **개발 전 테스트용.** 전압 레인지가 바뀌어 신규 데이터와 비교 안 함 → `data_origin='legacy_import'` 로 배제 |

### 6-4. 작업 순서 ★

**순서를 정하는 핵심 사실 하나** — `heatmap` 을 올려보낼 경로가 **아직 없다.**
AOS Twin scan(`0x80/0x82/0x86`)은 8절의 미구현 항목이다.
**DB 의 주 데이터 공급원이 펌웨어 쪽에 막혀 있다.**

그래서 **기존 `.dat` 샘플을 임포트하는 것이 전체 일정을 푸는 열쇠**가 된다.
샘플 10~20개를 넣으면 heatmap 이 **수만 장** 생기고, UDP 로 단 1 byte 도 오기 전에
API 와 대시보드를 **끝까지 만들고 시연할 수 있다.**

> 관통 원칙 세 가지
> 1. **읽기부터, 쓰기는 나중에**
> 2. **`udp_server.py` 는 가장 늦게, 가장 조금 건드린다** (실장비가 조용히 오동작한다)
> 3. **각 단계는 눈에 보이는 결과로 끝난다**

| 단계 | 할 일 | 서버 수정 | 끝나면 보이는 것 |
|---|---|---|---|
| **0** | `schema.sql` 적용 (개발 DB) | **없음** | 테이블 |
| **1** | **`.dat` 임포터** + PCSW 뷰어와 Idf 대조 | **없음** | DB 에 heatmap 수만 장 · **회귀 기준점** |
| **2** | **읽기 전용 FastAPI** + 대시보드 heatmap | **없음** | Air 갈아끼우며 heatmap 조회 |
| **3** | 실시간 전류 — `deque` + WebSocket | **읽기 추가만** | 메뉴얼 모드 실시간 그래프 |
| **4** | GFC 텔레메트리 저장 (큐 + writer + 파티션) | **쓰기 추가** | run 중 농도 그래프 · 종료 시 자동 삭제 |
| **5** | 제어 — 락 · 토큰 · `control_action` | 제어 경로 | 웹에서 파라미터 변경 |
| **6** | **AOS Twin scan 실측 경로** (STM32 ↔ 브리지 ↔ 서버 ↔ DB) | 신규 명령 | 실제 8시간 측정 · 중단/재개 |

**왜 이 순서인가**

- **0~2 단계는 `udp_server.py` 를 건드리지 않는다.** 실장비 위험 없이 설계의 핵심
  (Air 갈아끼우기, `pair_stat`, heatmap 표현)이 **쓸 만한지 먼저 검증**된다.
  여기서 스키마가 틀렸다면 아직 고치기 쉽다
- **1 단계가 2~5 단계를 펌웨어 일정에서 떼어낸다.** 이것이 임포터의 진짜 목적이다
  (측정 이력 축적이 아니다 — 그 run 들은 `legacy_import` 라 비교 후보에 뜨지도 않는다)
- **6 단계를 마지막에 두면 검증이 쉽다.** DB·API·대시보드·재개 로직이 이미 다 돌고 있으니
  실측 데이터가 들어오는 즉시 눈으로 확인된다. 반대 순서였다면 **뭐가 틀렸는지 알 수 없다**
- 3 → 4 → 5 는 서버 수정 **위험도 순**이다. 읽기 추가 → 쓰기 추가 → 제어 경로

**⚠️ 사람이 둘이면** 6 단계의 **펌웨어 쪽(STM32 Twin scan)은 0 단계부터 병렬로 시작**할 것.
가장 긴 작업이고 나머지와 의존성이 없다.

### 6-5. 건드릴 때 주의 (기존 경고 유지)

- **`test_packets.py` 를 먼저 돌릴 것.** 프레임·변환이 깨지면 장비가 조용히 오동작한다
- `udp_server.py` 의 수신 경로는 **블로킹하면 안 된다.** DB 쓰기를 동기로 넣으면
  UDP 처리가 밀린다 → 큐에 넣고 별도 태스크에서 쓰는 형태로
- 큐가 포화되면 **GFC 텔레메트리를 먼저 버린다. heatmap 은 절대 버리지 않는다**
- 콘솔로 내려보내는 push 는 **값이 바뀔 때만** 이다 (E13). 이 규칙을 깨면 값이 되돌아간다
- 장치 하향은 **NAT 매핑에 의존한다** (4절). 서버가 먼저 말을 걸 수 없다
- **DB 포트(5432)는 어느 망에도 열지 않는다** (W7). 실험실 망이 2개로 갈려 있다
